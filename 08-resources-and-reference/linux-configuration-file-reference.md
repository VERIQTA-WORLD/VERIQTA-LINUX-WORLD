# Linux configuration file reference

[Reference library](README.md) · [Filesystem reference](linux-filesystem-reference.md) · [Configuration changes and rollback](../06-system-administration/configuration-changes-and-rollback.md)

## Scope and environment

Use this page to identify who reads a configuration file, which source takes precedence and how you can check a candidate before changing a running system. A file can contain valid syntax while expressing an invalid or unsuitable configuration. A successful validation can also leave the running service unchanged.

Examples cover common GNU/systemd Linux installations. Package defaults, alternative init systems, containers and declarative systems differ. Use your installed manual and distribution guide for the actual release. The reference table is a discovery map; it does not authorize editing every listed file.

The follow-along exercise needs Bash, Python 3, an ordinary account and this repository's `06-system-administration/labs/check_demo_config.py`. Run from the repository root. You create private JSON examples only; you do not change a service, network manager, authentication policy or system configuration.

## Reference

### Ask six questions before changing a file

1. **Consumer:** which program reads it, and in which account, container or namespace?
2. **Owner:** is it administrator maintained, generated by a manager, package owned or built from a declarative source?
3. **Selection:** which main file, includes, drop-ins, environment values or command-line arguments actually apply?
4. **Validation:** which tool checks syntax, semantic values and cross-file requirements? What does it leave unchecked?
5. **Activation:** is it read once, on reload, on restart, at login, at boot or during a build/deployment?
6. **Recovery:** what exact previous input and activation step can you restore, and how will you verify the outcome?

The [UAPI configuration specification](https://uapi-group.org/specifications/specs/configuration_files_specification/) describes a useful vendor/local/runtime configuration pattern. It does not establish precedence rules for every application. “The last value always wins” and “everything in `/etc` overrides everything else” are unsafe universal rules.

### Identity, shell and access

| File or source | Consumer and purpose | Validation, activation and cautions |
| --- | --- | --- |
| `/etc/passwd`, `/etc/group` | Local account/group metadata | Prefer account-management tools; external identity services may also supply accounts. Use `getent` to query configured name service |
| `/etc/shadow`, `/etc/gshadow` | Restricted authentication/group metadata | Preserve permissions; do not include contents in public evidence or hand-edit as a beginner exercise |
| `/etc/nsswitch.conf` | glibc name-service lookup policy | Order and action clauses matter; a library or application may use another resolver implementation |
| `/etc/pam.d/*` | PAM service authentication/session policy | A bad change can lock you out. A syntax-looking success does not prove every authentication path works |
| `/etc/sudoers`, `/etc/sudoers.d/*` | sudo authorization policy | `visudo -c` checks policy syntax; test a separate candidate with `visudo -cf FILE` before installation. Syntax does not prove intended privilege boundaries |
| `/etc/ssh/sshd_config`, included server fragments | OpenSSH server policy | `sshd -t` checks configuration and key sanity; `sshd -T` exposes effective settings, with `-C` context needed to evaluate relevant `Match` conditions. Keep an existing recovery session |
| `/etc/ssh/ssh_config`, `~/.ssh/config` | OpenSSH client policy | `ssh -G HOST` evaluates client configuration without opening the SSH connection. Protect private keys and understand host-specific selection |
| `/etc/profile`, `~/.bash_profile`, `~/.bash_login`, `~/.profile` | Login shell setup when applicable | Bash reads login startup files according to its documented selection order; it does not automatically read every file listed |
| `~/.bashrc` | Interactive non-login Bash setup | `bash -n FILE` checks shell syntax only. Sourcing a file executes it in your current shell |
| `/etc/environment` | Environment input used by components such as `pam_env` | Not a general shell script; variable expansion and loading depend on the consumer |

OpenSSH server options often use the first obtained value, with documented exceptions. Includes and `Match` rules make context important. Do not transfer a generic “last line wins” mental model from another format. See the [OpenSSH configuration manuals](https://www.openssh.com/manual.html).

### Services and scheduled work

| File or source | Consumer and purpose | Validation, activation and cautions |
| --- | --- | --- |
| `/etc/systemd/system/*.service` and `*.d/*.conf` | Local systemd unit definitions/overrides | Inspect `systemctl cat UNIT` and `systemctl show UNIT -p FragmentPath -p DropInPaths`; evaluate applicable unit search paths |
| `/usr/lib/systemd/system` or a distribution equivalent | Packaged systemd units | Prefer supported local overrides to edits that package updates can replace |
| `/run/systemd/system` | Runtime systemd definitions/overrides | Commonly lost at reboot; runtime state is not a persistent configuration backup |
| `~/.config/systemd/user` | Per-user systemd units | Use the correct user manager; `systemctl --user` is distinct from the system manager |
| Systemd unit candidates | Service metadata and execution settings | `systemd-analyze verify FILE` checks supported unit properties and dependencies; `daemon-reload` reloads manager definitions, not the application configuration itself |
| `/etc/crontab`, `/etc/cron.d/*` | System cron schedules | System format usually includes a user field; a user's crontab does not. Implementation-specific validation options vary |
| User crontabs | Per-user scheduled jobs | Inspect your own with `crontab -l`; installing a crontab can replace the current table. Environment and working-directory assumptions need explicit treatment |
| Systemd timer/service pairs | Scheduled activation | Calendar syntax, timer persistence and service behavior are separate questions; use installed `systemd-analyze calendar` help |
| `/etc/logrotate.conf`, `/etc/logrotate.d/*` | Rotation policy for configured file logs | `logrotate --debug FILE` previews decisions without normal rotation, but inspect scripts and version semantics before operational use |
| `/etc/systemd/journald.conf` and supported drop-ins | Journal storage/forwarding/retention policy | Read effective version-specific configuration; restarting or reloading another component does not automatically apply journald policy |

A service's `ExecStart` may point at an entirely different configuration file than the one you expected. Inspect the actual command and documentation without publishing secrets passed through arguments or environment. A unit can be syntactically valid yet fail because an executable, credential, mount or permission is missing.

### Networking, storage and kernel parameters

| File or source | Consumer and purpose | Validation, activation and cautions |
| --- | --- | --- |
| `/etc/hosts` | Static host-name entries | Name-service order and application behavior determine use; it is not a DNS zone file |
| `/etc/resolv.conf` | Resolver input, often manager generated | Inspect its link target and active manager before editing. A local stub address is not necessarily an upstream server |
| `/etc/systemd/resolved.conf` and drop-ins | systemd-resolved policy | Per-link settings can come from network managers; `resolvectl status` shows current manager state when available |
| `/etc/netplan/*.yaml` | Netplan input on systems using it | `netplan generate` is a generator action that can write backend files; use an isolated root or a disposable VM for experiments. `netplan try` has documented rollback limitations |
| `/etc/NetworkManager/system-connections/*` | NetworkManager connection profiles | Use supported tools and restrictive permissions. Profile reload and connection activation are different operations |
| `/etc/systemd/network/*` | systemd-networkd link/network configuration | File matching and ordering determine selection; applying changes can interrupt remote access |
| `/etc/fstab` | Persistent filesystem mount definitions | `findmnt --verify --tab-file FILE` checks a candidate with version-specific limits; `mount -a` performs mounts and is not a harmless validator |
| `/etc/crypttab` | Encrypted-volume activation policy | Boot integration, keys and initramfs may need coordinated changes; ordinary syntax checks do not prove unlock/recovery |
| `/etc/sysctl.conf`, `sysctl.d` sources | Kernel parameter inputs | `sysctl --system` applies values; it is not a dry run. Effective values can also change through other tools or namespaces |
| `/etc/modprobe.d/*` | Module loading/options policy | Affects supported module-management paths; a built-in driver or initramfs copy may require another procedure |
| `/etc/default/grub`, distribution boot tooling | Inputs to boot-loader configuration generation | Generation and installation paths vary. Do not assume one distribution's update command is universal |

Use a console or another verified recovery route for changes that can sever SSH, networking, authentication or boot. For hands-on operational procedures, use the [administration collection](../06-system-administration/README.md); this page concentrates on identifying the right input and consumer.

### Packages, applications and user preferences

| Source | Consumer and purpose | Interpretation |
| --- | --- | --- |
| `/etc/apt/sources.list`, `/etc/apt/sources.list.d/*` | APT repository definitions | Deb822 `.sources` and traditional `.list` formats differ; inspect trust configuration as well as URLs |
| `/etc/apt/preferences`, `preferences.d/*` | APT version selection preferences | Pinning can alter upgrades; inspect candidate versions before changing policy |
| `/etc/dnf/dnf.conf`, `/etc/yum.repos.d/*` | DNF/repository policy on applicable releases | DNF major versions and plugins differ; directory names can persist across tool generations |
| Application-specific configuration under `/etc` | Service/application options | Use the application's validator, not merely a generic JSON/YAML/TOML parser |
| `$XDG_CONFIG_HOME` or its documented fallback | Participating user applications | Some applications still use legacy dotfiles; XDG is not automatically implemented everywhere |
| Declarative configuration repositories | Source for generated host/user state | Edit the declared source and deploy through its tool; direct edits to generated outputs can disappear |

## Follow along

A port number of `70000` is valid JSON but outside this demonstration application's accepted range. You will observe that distinction, then accept a corrected candidate. This uses the existing small validator from folder 6 rather than claiming to validate real service configuration.

From the repository root, confirm `06-system-administration/labs/check_demo_config.py` exists, then run:

<!-- reference:exercise -->
```bash
config_lab=$(mktemp -d) || exit 1
printf '%s\n' '{"port":70000,"message":"reference example"}' > "$config_lab/candidate.json"
python3 -m json.tool "$config_lab/candidate.json" > "$config_lab/parsed.json"
if python3 06-system-administration/labs/check_demo_config.py "$config_lab/candidate.json" > "$config_lab/rejected.txt" 2>&1; then
    echo 'FAIL: invalid application value was accepted' >&2
    exit 1
else
    config_status=$?
    test "$config_status" -eq 2 || exit 1
    echo 'PASS: JSON parser accepted syntax; application validator rejected port 70000'
fi
printf '%s\n' '{"port":8000,"message":"reference example"}' > "$config_lab/candidate.json"
python3 06-system-administration/labs/check_demo_config.py "$config_lab/candidate.json"
cp -- "$config_lab/candidate.json" "$config_lab/accepted.json"
cmp -- "$config_lab/candidate.json" "$config_lab/accepted.json"
echo 'PASS: corrected candidate accepted and preserved byte for byte'
```

The example's `exit 1` stops the shell running these commands if an assumption fails. Run it in a disposable Bash session if you want that session isolated from your normal work.

## Verify your result

Expect two `PASS` lines and `Demo configuration accepted`. Inspect `rejected.txt` to find the range error. The rejected candidate's expected status is `2`; a missing interpreter or missing script must not be mistaken for a successful rejection test.

Explain the three separate results: JSON parsing succeeded, application validation initially failed, and the corrected candidate was copied intact. No service loaded either file. This exercise does not establish reload support, production suitability, file ownership, secret protection or rollback behavior for a real application.

## Cleanup

<!-- reference:cleanup -->
```bash
rm -i -- "$config_lab/candidate.json" "$config_lab/parsed.json" "$config_lab/rejected.txt" "$config_lab/accepted.json"
rmdir -- "$config_lab"
```
