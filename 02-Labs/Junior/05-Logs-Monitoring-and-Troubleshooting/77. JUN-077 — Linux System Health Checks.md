# Part 1 — Define healthy before collecting commands

“Healthy” is meaningful only within a stated contract. For a small web application, it might require adequate resource headroom, the intended process and listeners, and a client operation returning expected content. Host uptime alone does not satisfy that contract.

Your lab contract requires six named observations: `cpu`, `memory`, `disk`, `process`, `network` and `application`. A successful resource observation means its specific check met a documented criterion; it does not mean that resource can never fail. Write the criterion and collection method beside each state.

The application observation must represent the user operation, not merely a systemd active state or successful TCP connection. The previous labs provide building blocks; your engineering judgment defines which evidence is sufficient for this service.

# Part 3 — Preserve collector status without losing it in a pipeline

If you save an observation, capture the command's status before another command replaces it. In this Linux-only example, a nonzero result remains visible:

```bash
df -Pk -- "$lab" > evidence/df.txt 2> evidence/df.stderr
collection_status=$?
printf 'df collection status: %s\n' "$collection_status"
cat evidence/df.txt

```

A collector error is an unknown observation unless you have another valid source. It is not a measured capacity failure and not a healthy default. A report file existing after redirection does not prove the command completed successfully.

This lab's JSON uses explicit `age_seconds` supplied by the collector. In a production collector, derive age from actual recorded timestamps and clock behavior. Do not type zero into an old observation simply to pass the freshness gate.

# Part 4 — Choose a transparent state model

| Input condition | Summary treatment |
| --- | --- |
| Fresh required check with `ok` | A supported pass for that named check |
| Fresh required check with `fail` | A supported failure for that named check |
| Fresh required check with `unknown` | Required outcome is not established |
| Missing required check | Explicit missing/unknown entry |
| Observation older than 60 seconds | Stale evidence, not current success |
| Duplicate or unexpected check name | Reject the file; do not let order decide |

Freshness is inclusive: age 60 seconds is accepted in this lab, 61 is stale. The overall state is `fail` when any fresh failure exists, otherwise `unknown` when anything required is missing, unknown or stale, otherwise `ok`. Both fail and unknown return attention.

The tool preserves stale failures in a separate list. Losing freshness does not erase the fact that the last known observation failed; it only limits what you can claim about now.

# Part 7 — Design the final tool before typing it

Your tool accepts one JSON evidence file. It reads at most 1 MiB, rejects malformed JSON, duplicate keys, nonfinite numbers, directories and final-component symbolic links, and validates the domain fields before printing a report. It never evaluates the input as shell or Python code.

| Exit status | Meaning |
| --- | --- |
| 0 | The documented analysis completed and its success criterion is met |
| 1 | Valid evidence requires attention, or the available evidence cannot establish the required outcome |
| 2 | Input, schema, range, collection or usage error; no normal report is printed |

A zero result concerns this tool's stated contract, not whole-system health. An attention result is different from malformed input. Your shell's status must be captured immediately after the command, before another command replaces it.

The report retains lists of failures, unknown/missing checks, stale checks and stale failures. Its deterministic precedence keeps real failure visible without concealing missing evidence. A positive state means all six supplied, fresh observations meet this lab contract.

The file checks assume your private workspace is trusted. They are not race-proof protection against a malicious writer changing parent directories or files during a read. Do not expose the tool as a privileged service or point it at hostile paths.

```bash
cat > scripts/health-summary.py <<'PY'
#!/usr/bin/env python3
"""Linux System Health Checks — bounded evidence analysis for this lab."""
import argparse
import datetime as dt
import json
import math
from pathlib import Path
import stat
import sys


def integer(value, name, low=0, high=10**18):
    if type(value) is not int or not low <= value <= high:
        raise ValueError(name + ': expected an integer in the documented range')
    return value


def number(value, name, low=0, high=10**12):
    if type(value) not in (int, float) or not math.isfinite(value) or not low <= value <= high:
        raise ValueError(name + ': expected a finite number in the documented range')
    return value


def text(value, name):
    if not isinstance(value, str) or not value.strip() or len(value) > 1000:
        raise ValueError(name + ': expected nonempty bounded text')
    if any(ord(c) < 32 or ord(c) == 127 for c in value):
        raise ValueError(name + ': control characters are not allowed')
    return value


def fields(obj, names):
    if not isinstance(obj, dict) or set(obj) != set(names.split()):
        raise ValueError('expected exactly these fields: ' + names)


def reject_duplicates(pairs):
    result = {}
    for key, value in pairs:
        if key in result:
            raise ValueError('duplicate JSON key')
        result[key] = value
    return result


def load(path):
    # A private, trusted lab workspace is a prerequisite, not a hostile-directory sandbox.
    if path.is_symlink() or not stat.S_ISREG(path.stat().st_mode):
        raise ValueError('input must be a regular non-symlink file')
    with path.open('rb') as stream:
        data = stream.read(1024 * 1024 + 1)
    if len(data) > 1024 * 1024:
        raise ValueError('input exceeds the 1 MiB lab limit')
    return json.loads(data.decode('utf-8'), object_pairs_hook=reject_duplicates,
                      parse_constant=lambda _: (_ for _ in ()).throw(ValueError('nonfinite JSON value')))


def analyze(doc):
    fields(doc, 'checks')
    required = {'cpu', 'memory', 'disk', 'process', 'network', 'application'}
    if not isinstance(doc['checks'], list) or len(doc['checks']) > 20:
        raise ValueError('checks: expected a bounded list')
    seen, failed, unknown, stale, stale_failures = set(), [], [], [], []
    for check in doc['checks']:
        fields(check, 'name state age_seconds evidence')
        name = text(check['name'], 'name')
        if name not in required or name in seen:
            raise ValueError('unexpected or duplicate check')
        seen.add(name)
        state = check['state']
        if state not in ('ok', 'fail', 'unknown'):
            raise ValueError('invalid observation state')
        age = number(check['age_seconds'], 'age_seconds', 0, 86400)
        text(check['evidence'], 'evidence')
        if age > 60:
            stale.append(name)
            if state == 'fail':
                stale_failures.append(name)
        elif state == 'fail':
            failed.append(name)
        elif state == 'unknown':
            unknown.append(name)
    missing = sorted(required - seen)
    overall = 'fail' if failed else ('unknown' if missing or stale or unknown else 'ok')
    return int(overall != 'ok'), {'overall': overall, 'failed': sorted(failed),
        'unknown': sorted(unknown), 'missing': missing, 'stale': sorted(stale),
        'stale_failures': sorted(stale_failures), 'freshness_limit_seconds': 60}


def main():
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument('input', type=Path, help='private lab JSON evidence file; never executed as code')
    args = parser.parse_args()
    try:
        status, report = analyze(load(args.input))
        print(json.dumps(report, sort_keys=True, indent=2, allow_nan=False))
        return status
    except (OSError, ValueError, TypeError, KeyError, OverflowError, RecursionError) as error:
        print('ERROR: ' + str(error), file=sys.stderr)
        return 2


if __name__ == '__main__':
    sys.exit(main())
PY
```

## Explain the implementation

`fields` rejects missing and unexpected object fields so a misspelling cannot silently become an absent observation. `integer` rejects booleans as numeric counters. `number` rejects nonfinite values. Those checks are deliberate: Python otherwise treats `True` as an integer, and permissive JSON parsers may accept nonstandard numeric constants.

`load` bounds the input size before decoding it and rejects duplicate keys. The `analyze` function contains your subject-specific decisions; walk through it with the supplied numbers and predict the report before running it. `main` prints JSON rather than terminal control sequences and keeps errors on stderr. It does not open a second evidence file, invoke a repair command or change host policy.

Your program has no execute permission requirement because you invoke it explicitly with `python3`. That keeps the interpreter choice visible. Do not run it as root merely because an input is inaccessible.

# Part 15 — Knowledge assessment

Answer these before reading the explanation. Demonstrate the answers with your own evidence where appropriate.

## 1. Why define the application operation first?

It determines what success means to a user; process existence alone cannot supply that meaning.

## 2. Can you average states into a health percentage?

That can conceal a critical failure or missing evidence; this lab uses explicit required checks.

## 3. What is the result with a missing application check?

Unknown overall unless a separate fresh failure exists; it never becomes ok.

## 4. What does a stale success prove about now?

It proves an earlier observed success only, outside the current freshness contract.

## 5. Why preserve stale failures separately?

They retain the last known problem while making current uncertainty explicit.

## 6. Is age 60 fresh?

Yes in this inclusive lab contract; age 61 is stale.

## 7. Why reject duplicate names?

Otherwise file order could silently choose one of contradictory observations.

## 8. Does command exit zero mean its resource is healthy?

No. It may successfully print an unhealthy state; interpret the result.

## 9. Why capture stderr and status?

An empty output file may result from a collector failure rather than a healthy empty observation.

## 10. What belongs in the handover?

Scope, collection time, acceptance criteria, actual evidence, unresolved checks and recovery/next actions.
