# Part 1 — Move from journal commands to an investigation

In JUN-069 you learned the logging components and built an investigation tool. In JUN-070 you explored journal queries. Here you use those skills to answer a narrower operational question: which recorded events belong to this investigation, and in what order?

Your fictional customer says the API failed at 09:15 UTC. The application recorded a dependency timeout at 09:13. A service restart appears at 09:14. The restart is later than the first timeout, so it cannot explain that earlier recorded timeout on ordering alone. It may be a response to it. That is a hypothesis to test, not a conclusion to paste into your report.

Create three columns in your notes: observation, possible explanation and next check. Keep an operator's report separate from a machine-generated event until you can correlate their clocks and scope.

# Part 2 — Map the source before reading its content

| Source | Useful observation | Limit you must retain |
| --- | --- | --- |
| Journal | Unit, boot, timestamp, priority and structured metadata | Your account may see only part of the journal; retention may exclude the incident. |
| Kernel messages | Device, memory, network and filesystem symptoms | A driver message is not a complete application diagnosis. |
| Authentication records | Login, authorization and session events | Absence of a visible event does not prove no access occurred. |
| Application log | Request, dependency, retry and application context | Message text and severity are application-defined, and data can contain secrets. |

On your Linux VM, inspect the available evidence without changing retention or logging policy:

```bash
journalctl --list-boots --no-pager
journalctl -b -n 20 --utc --no-pager
journalctl -b -k -n 10 --utc --no-pager
ls -ld /var/log
ls -l /var/log/syslog /var/log/auth.log
```

The final listing can report absent files. That is an observation, not a broken lab. Traditional text logs depend on installed components and configuration. Do not create empty files to imitate another distribution. Record which source exists, which interval it covers and what your account can read.

# Part 3 — Choose a bounded window and preserve provenance

Start with a small interval around a known symptom. The following historical window is illustrative; replace the two timestamps with an actual interval visible on your VM before executing it:

```bash
journalctl --since '2026-11-04 09:10:00 UTC'   --until '2026-11-04 09:20:00 UTC' --utc --no-pager -n 50
```

A zero-row query might mean no matching records, wrong time, insufficient access, different boot or expired retention. It does not establish that the host was healthy. Record the exact query, host and observation time next to any extracted evidence.

Use `journalctl -o json` for structured inspection when you need metadata, and retain original bytes privately before making a redacted copy. The final tool below accepts your deliberately small lab schema, not raw journal export. Do not claim it implements the journal file format or every syslog grammar.

# Part 4 — Interpret timestamps before sorting

A timestamp without a timezone cannot be placed reliably beside an explicitly UTC event. A timezone offset allows conversion to UTC; it does not prove that the source clock was synchronized. Within a boot, monotonic journal metadata can help investigate wall-clock changes, but your supplied fixture uses aware wall-clock timestamps only.

Your tool normalizes offsets, rejects naive timestamps and requires a single host/boot pair. These restrictions keep the exercise honest. If you need to correlate across hosts, first establish clock offsets and an uncertainty window. Do not quietly sort two unsynchronized clocks and call the result a causal chain.

Manually order these equivalent times: `09:13:00+00:00` and `10:13:00+01:00`. They describe the same instant. If two records have equal time, the tool retains their input order; that order is a presentation choice, not evidence that one event preceded the other.

# Part 6 — Define the evidence contract

Each synthetic record has exactly `host`, `boot`, `time`, `source` and `message`. Host and boot are lab labels, not automatic discoveries. `source` is one of `application`, `service` or `kernel`; the small allowlist makes misspellings visible. `time` is an ISO timestamp with timezone information. The final tool requires 1–200 records and normalizes them to UTC.

A single boot scope prevents a restart on a different boot from being silently merged with the incident. Duplicate event records remain visible; the tool does not invent a deduplication rule. Each event includes its source so you can distinguish application observation from service-manager evidence.

# Part 8 — Design the final tool before typing it

Your tool accepts one JSON evidence file. It reads at most 1 MiB, rejects malformed JSON, duplicate keys, nonfinite numbers, directories and final-component symbolic links, and validates the domain fields before printing a report. It never evaluates the input as shell or Python code.

| Exit status | Meaning |
| --- | --- |
| 0 | The documented analysis completed and its success criterion is met |
| 1 | Valid evidence requires attention, or the available evidence cannot establish the required outcome |
| 2 | Input, schema, range, collection or usage error; no normal report is printed |

A zero result concerns this tool's stated contract, not whole-system health. An attention result is different from malformed input. Your shell's status must be captured immediately after the command, before another command replaces it.

The report sorts aware timestamps after converting them to UTC, reports the recorded span in seconds and retains the source and message. It refuses mixed host/boot scope. A three-event timeline is a sequence of recorded observations, not proof of the outage cause.

The file checks assume your private workspace is trusted. They are not race-proof protection against a malicious writer changing parent directories or files during a read. Do not expose the tool as a privileged service or point it at hostile paths.

<!-- lab:implementation -->
```bash
cat > scripts/system-log-timeline.py <<'PY'
#!/usr/bin/env python3
"""Reading System Logs — bounded evidence analysis for this lab."""
import argparse
import datetime as dt
import json
import math
from pathlib import Path
import stat
import sys


def integer(value, name, low=0, high=10**18):
    if type(value) is not int or not low <= value <= high:
        raise ValueError(name + ': expected an integer in the documented range')
    return value


def number(value, name, low=0, high=10**12):
    if type(value) not in (int, float) or not math.isfinite(value) or not low <= value <= high:
        raise ValueError(name + ': expected a finite number in the documented range')
    return value


def text(value, name):
    if not isinstance(value, str) or not value.strip() or len(value) > 1000:
        raise ValueError(name + ': expected nonempty bounded text')
    if any(ord(c) < 32 or ord(c) == 127 for c in value):
        raise ValueError(name + ': control characters are not allowed')
    return value


def fields(obj, names):
    if not isinstance(obj, dict) or set(obj) != set(names.split()):
        raise ValueError('expected exactly these fields: ' + names)


def reject_duplicates(pairs):
    result = {}
    for key, value in pairs:
        if key in result:
            raise ValueError('duplicate JSON key')
        result[key] = value
    return result


def load(path):
    # A private, trusted lab workspace is a prerequisite, not a hostile-directory sandbox.
    if path.is_symlink() or not stat.S_ISREG(path.stat().st_mode):
        raise ValueError('input must be a regular non-symlink file')
    with path.open('rb') as stream:
        data = stream.read(1024 * 1024 + 1)
    if len(data) > 1024 * 1024:
        raise ValueError('input exceeds the 1 MiB lab limit')
    return json.loads(data.decode('utf-8'), object_pairs_hook=reject_duplicates,
                      parse_constant=lambda _: (_ for _ in ()).throw(ValueError('nonfinite JSON value')))


def analyze(doc):
    fields(doc, 'events')
    events = doc['events']
    if not isinstance(events, list) or not 1 <= len(events) <= 200:
        raise ValueError('events: expected 1..200 records')
    parsed = []
    scope = set()
    for item in events:
        fields(item, 'host boot time source message')
        host = text(item['host'], 'host')
        boot = text(item['boot'], 'boot')
        source = text(item['source'], 'source')
        if source not in ('application', 'service', 'kernel'):
            raise ValueError('unknown source')
        message = text(item['message'], 'message')
        stamp = dt.datetime.fromisoformat(text(item['time'], 'time').replace('Z', '+00:00'))
        if stamp.tzinfo is None or stamp.utcoffset() is None:
            raise ValueError('time requires a timezone')
        stamp = stamp.astimezone(dt.timezone.utc)
        scope.add((host, boot))
        parsed.append((stamp, source, message))
    if len(scope) != 1:
        raise ValueError('select one host and boot before correlation')
    parsed.sort(key=lambda row: row[0])
    host, boot = next(iter(scope))
    return 0, {'host': host, 'boot': boot, 'events': len(parsed),
               'span_seconds': (parsed[-1][0] - parsed[0][0]).total_seconds(),
               'timeline': [{'utc': stamp.isoformat(), 'source': source, 'message': message}
                            for stamp, source, message in parsed],
               'cause': 'not established by ordering alone'}


def main():
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument('input', type=Path, help='private lab JSON evidence file; never executed as code')
    args = parser.parse_args()
    try:
        status, report = analyze(load(args.input))
        print(json.dumps(report, sort_keys=True, indent=2, allow_nan=False))
        return status
    except (OSError, ValueError, TypeError, KeyError, OverflowError, RecursionError) as error:
        print('ERROR: ' + str(error), file=sys.stderr)
        return 2


if __name__ == '__main__':
    sys.exit(main())
PY
```

## Explain the implementation

`fields` rejects missing and unexpected object fields so a misspelling cannot silently become an absent observation. `integer` rejects booleans as numeric counters. `number` rejects nonfinite values. Those checks are deliberate: Python otherwise treats `True` as an integer, and permissive JSON parsers may accept nonstandard numeric constants.

`load` bounds the input size before decoding it and rejects duplicate keys. The `analyze` function contains your subject-specific decisions; walk through it with the supplied numbers and predict the report before running it. `main` prints JSON rather than terminal control sequences and keeps errors on stderr. It does not open a second evidence file, invoke a repair command or change host policy.

Your program has no execute permission requirement because you invoke it explicitly with `python3`. That keeps the interpreter choice visible. Do not run it as root merely because an input is inaccessible.

# Part 16 — Knowledge assessment

Answer these before reading the explanation. Demonstrate the answers with your own evidence where appropriate.

## 1. Why is the restart not automatically the cause?

The first recorded timeout precedes it. The restart might be a response; you need independent evidence to establish the failure mechanism.

## 2. Why record the boot identifier?

It separates event contexts that might otherwise reuse a hostname and clock times across reboots.

## 3. Does UTC conversion synchronize clocks?

No. It changes the representation of an instant according to its offset; a source clock can still be wrong.

## 4. What does an empty journal query establish?

Only that your query returned no visible matches under its current time, boot, access and retention scope.

## 5. Why retain source names?

An application message and a manager action have different provenance and support different conclusions.

## 6. Can you parse raw journal JSON with this schema?

No. The lab schema is intentionally smaller and must not be mistaken for a complete journal export parser.

## 7. What happens to equal timestamps?

Stable sorting retains input order, which is not proof of event precedence.

## 8. Why reject mixed boots instead of guessing?

A guessed merge hides a scope change that could invalidate the incident narrative.

## 9. Should duplicate records disappear automatically?

No. You need an explicit, justified identity rule before deduplicating potentially distinct events.

## 10. How do you test the timeline independently?

Calculate the offset conversion and 120-second span manually, then compare the ordered messages and sources with the output.

## 11. Does the fixture describe your running VM?

No. It is supplied synthetic evidence with known expected results. Host observations need their own provenance and collection context.

## 12. What does a parser success establish?

Only that the supplied data satisfied its syntax and schema checks. It does not prove that the input is truthful or the service is healthy.

## 13. Why is unknown different from zero?

Zero is a measurement; unknown is missing or insufficient evidence. Treating them as equivalent can hide a real problem.

## 14. Why capture an exit status immediately?

Another command replaces the shell’s most recent status. Record it before printing, formatting or running another check.

## 15. Why keep the normal fixture unchanged?

It gives you a reproducible baseline for distinguishing a broken implementation from a deliberately changed candidate.

## 16. Why avoid sudo for the final tool?

It reads private supplied files and needs no administrative authority. More privilege changes the risk and may hide an access defect.

## 17. Can a symlink check secure an untrusted directory?

No. Path components and contents can change during checks. This lab assumes a private trusted workspace and does not provide a hostile-filesystem sandbox.

## 18. Why bound input size and sample duration?

Bounds constrain the teaching workload and make accidental resource consumption easier to reason about. They are not comprehensive service hardening.

## 19. What should you preserve before cleanup?

Sanitized code, input provenance, actual test results and the report needed to explain your experiment; keep secrets and unrelated data private.

## 20. When is the lab complete?

When the relevant acceptance criteria pass, you can explain the result independently and cleanup or deliberate retention is verified.
