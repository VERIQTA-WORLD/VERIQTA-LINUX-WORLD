# Part 1 — Start with the affected operation

A useful symptom is specific: “the rendered response differs from the expected greeting in this workspace.” “Linux is broken” does not identify a boundary or an acceptance check.

Your first question is what the user expected and what actually happened. Preserve the exact failing result, time and scope. List what still works: the file exists, it is readable and the command completed. Those facts narrow the question without proving why its contents differ.

Avoid the reflex to restart, reinstall or elevate privileges. None of those actions addresses a content comparison until you establish a causal path. Your smallest safe test is to inspect the input and compare bytes.

# Part 2 — Reproduce the complete incident safely

This exercise creates only three private files. Follow the checks in order. The expected mismatch is handled explicitly so an error reading a file is not mistaken for the intended failure:

<!-- lab:exercise-078 -->
```bash
printf 'Hello from your Linux lab\n' > fixtures/expected.txt
cp fixtures/expected.txt evidence/response.txt
cp evidence/response.txt evidence/response.baseline
cmp -- fixtures/expected.txt evidence/response.txt
printf 'Hello from the wrong configuration\n' > evidence/response.txt
if cmp -- fixtures/expected.txt evidence/response.txt; then
    printf 'Unexpected match: the fault was not reproduced\n' >&2
    exit 1
else
    comparison_status=$?
    test "$comparison_status" -eq 1 || exit "$comparison_status"
    printf 'Expected content mismatch observed\n'
fi
ls -l evidence/response.txt
cat evidence/response.txt
cp evidence/response.baseline evidence/response.txt
for sample in 1 2 3; do
    cmp -- fixtures/expected.txt evidence/response.txt || exit 1
    printf 'Recovery sample %s passed\n' "$sample"
done
```

Expect an initial match, an explicitly identified mismatch, then three recovery passes. `cmp` status 1 means different bytes; status 2 means a trouble condition such as inaccessible input. Your test distinguishes those meanings rather than treating every nonzero status as the same fault.

The repair restores your known baseline. In a real service, copying a file may require validation, metadata preservation and activation; this tiny example does not establish those requirements for another application.

# Part 3 — Compare hypotheses before selecting one

For the wrong-content symptom, consider at least two explanations:

| Hypothesis | Discriminating check | Result in this exercise |
| --- | --- | --- |
| The response is unreadable | Read it as the affected account and capture status | You can read it; this contradicts that explanation. |
| The configured content changed | Compare current bytes with the preserved baseline | The bytes differ; this supports the change explanation. |
| The client checked a different path | Record the exact paths and rerun the original comparison | Your local exercise fixes the paths; a remote incident would need more context. |

Support for a hypothesis is not a complete causal proof. Record how the change happened and which observation rules out an alternative. If you cannot establish the mechanism, state that limit instead of filling the root-cause field with a guess.

# Part 4 — Choose a change with a stop condition

Before applying a repair, state its exact scope, compatible previous state, intended effect and rollback trigger. Change one thing at a time when possible. If the predicted result does not occur, stop and reassess rather than stacking unrelated changes.

For this exercise, the predicted repair effect is byte equality with the original greeting. The preserved baseline supplies a compatible previous state, and the three comparisons repeat the affected operation. File existence alone would not satisfy the acceptance criterion.

Keep diagnostic collection distinct from repair. A successful `ls` is a fact about directory visibility, not authorization to overwrite an unrelated configuration file.

# Part 5 — Design a useful incident record

Your JSON contains a symptom, an acceptance statement, baseline/failure observations, two or more hypotheses with test descriptions, a selected hypothesis, repair description and three recovery outcomes.

The tool checks record completeness and consistency. It cannot know whether you actually ran the tests or whether the chosen explanation is scientifically correct. A `supported` label is your evidence-based assertion and must be backed by raw observations in the report.

Unknown or untested alternatives remain visible. To pass this exercise, select a supported hypothesis, document at least one contradicted alternative, record the repair and show three successful recovery checks. A single successful sample is deliberately insufficient for this small contract.

# Part 7 — Design the final tool before typing it

Your tool accepts one JSON evidence file. It reads at most 1 MiB, rejects malformed JSON, duplicate keys, nonfinite numbers, directories and final-component symbolic links, and validates the domain fields before printing a report. It never evaluates the input as shell or Python code.

| Exit status | Meaning |
| --- | --- |
| 0 | The documented analysis completed and its success criterion is met |
| 1 | Valid evidence requires attention, or the available evidence cannot establish the required outcome |
| 2 | Input, schema, range, collection or usage error; no normal report is printed |

A zero result concerns this tool's stated contract, not whole-system health. An attention result is different from malformed input. Your shell's status must be captured immediately after the command, before another command replaces it.

A passing result means the supplied record meets the documented evidence checklist. It is not automatic root-cause validation. Missing support, untested alternatives and unstable recovery remain attention conditions rather than being silently promoted to success.

The file checks assume your private workspace is trusted. They are not race-proof protection against a malicious writer changing parent directories or files during a read. Do not expose the tool as a privileged service or point it at hostile paths.

# Part 8 — Implement your tool

<!-- lab:implementation -->
```bash
cat > scripts/investigation-record.py <<'PY'
#!/usr/bin/env python3
"""Basic Linux Troubleshooting — bounded evidence analysis for this lab."""
import argparse
import datetime as dt
import json
import math
from pathlib import Path
import stat
import sys


def integer(value, name, low=0, high=10**18):
    if type(value) is not int or not low <= value <= high:
        raise ValueError(name + ': expected an integer in the documented range')
    return value


def number(value, name, low=0, high=10**12):
    if type(value) not in (int, float) or not math.isfinite(value) or not low <= value <= high:
        raise ValueError(name + ': expected a finite number in the documented range')
    return value


def text(value, name):
    if not isinstance(value, str) or not value.strip() or len(value) > 1000:
        raise ValueError(name + ': expected nonempty bounded text')
    if any(ord(c) < 32 or ord(c) == 127 for c in value):
        raise ValueError(name + ': control characters are not allowed')
    return value


def fields(obj, names):
    if not isinstance(obj, dict) or set(obj) != set(names.split()):
        raise ValueError('expected exactly these fields: ' + names)


def reject_duplicates(pairs):
    result = {}
    for key, value in pairs:
        if key in result:
            raise ValueError('duplicate JSON key')
        result[key] = value
    return result


def load(path):
    # A private, trusted lab workspace is a prerequisite, not a hostile-directory sandbox.
    if path.is_symlink() or not stat.S_ISREG(path.stat().st_mode):
        raise ValueError('input must be a regular non-symlink file')
    with path.open('rb') as stream:
        data = stream.read(1024 * 1024 + 1)
    if len(data) > 1024 * 1024:
        raise ValueError('input exceeds the 1 MiB lab limit')
    return json.loads(data.decode('utf-8'), object_pairs_hook=reject_duplicates,
                      parse_constant=lambda _: (_ for _ in ()).throw(ValueError('nonfinite JSON value')))


def analyze(doc):
    fields(doc, 'symptom acceptance baseline_ok failure_observed hypotheses selected repair recovery')
    for key in ('symptom', 'acceptance'):
        text(doc[key], key)
    for key in ('baseline_ok', 'failure_observed'):
        if type(doc[key]) is not bool:
            raise ValueError(key + ': boolean required')
    hypotheses = doc['hypotheses']
    if not isinstance(hypotheses, list) or not 2 <= len(hypotheses) <= 10:
        raise ValueError('two to ten hypotheses required')
    found = {}
    for item in hypotheses:
        fields(item, 'name test result')
        name = text(item['name'], 'hypothesis name')
        text(item['test'], 'test')
        if name in found or item['result'] not in ('supported', 'contradicted', 'untested'):
            raise ValueError('duplicate hypothesis or invalid result')
        found[name] = item['result']
    if doc['selected'] is not None and doc['selected'] not in found:
        raise ValueError('selected hypothesis not declared')
    if doc['repair'] is not None:
        text(doc['repair'], 'repair')
    recovery = doc['recovery']
    if not isinstance(recovery, list) or len(recovery) > 20 or any(type(x) is not bool for x in recovery):
        raise ValueError('recovery: bounded boolean list required')
    gaps = []
    if not doc['baseline_ok']: gaps.append('healthy baseline not recorded')
    if not doc['failure_observed']: gaps.append('failure not observed')
    if found.get(doc['selected']) != 'supported': gaps.append('selected explanation not supported')
    if 'contradicted' not in found.values(): gaps.append('alternative not ruled out')
    if doc['repair'] is None: gaps.append('repair missing')
    if len(recovery) < 3 or not all(recovery): gaps.append('recovery not demonstrated')
    return int(bool(gaps)), {'record': 'incomplete' if gaps else 'checklist-complete',
                             'gaps': gaps, 'truth_of_claims': 'requires reviewer evidence'}


def main():
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument('input', type=Path, help='private lab JSON evidence file; never executed as code')
    args = parser.parse_args()
    try:
        status, report = analyze(load(args.input))
        print(json.dumps(report, sort_keys=True, indent=2, allow_nan=False))
        return status
    except (OSError, ValueError, TypeError, KeyError, OverflowError, RecursionError) as error:
        print('ERROR: ' + str(error), file=sys.stderr)
        return 2


if __name__ == '__main__':
    sys.exit(main())
PY
```

## Explain the implementation

`fields` rejects missing and unexpected object fields so a misspelling cannot silently become an absent observation. `integer` rejects booleans as numeric counters. `number` rejects nonfinite values. Those checks are deliberate: Python otherwise treats `True` as an integer, and permissive JSON parsers may accept nonstandard numeric constants.

`load` bounds the input size before decoding it and rejects duplicate keys. The `analyze` function contains your subject-specific decisions; walk through it with the supplied numbers and predict the report before running it. `main` prints JSON rather than terminal control sequences and keeps errors on stderr. It does not open a second evidence file, invoke a repair command or change host policy.

Your program has no execute permission requirement because you invoke it explicitly with `python3`. That keeps the interpreter choice visible. Do not run it as root merely because an input is inaccessible.
